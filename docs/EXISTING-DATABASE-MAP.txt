How this was discovered
-----------------------
Only the publishable key from .env.local was used. No row was read and nothing was written.
The PostgREST schema listing needs a secret key, so tables and columns were found from error replies:
- GET /rest/v1/<table>?select=*&limit=0 → 42501 "permission denied" means the table exists; PGRST205 means it doesn't (the hint names the closest real table).
- GET /rest/v1/<table>?select=<col>&limit=0 → 42501 means the column exists; 42703 means it doesn't. Postgres resolves names before it checks privileges.
- GET /rest/v1/<table>?<col>=eq.<junk> → the 22P02 message names the column's type.
Nullability, defaults and CHECK constraints can't be seen this way. Where a table matches the Proviyaa OS repo (loki1514/Repo-1-, supabase/migrations 0001–0020) column for column, those come from the repo migration.

The live database is the shared Proviyaa OS database, but it is NOT identical to the OS repo's main branch.
Differences:
- organizations has id, business_name, status, email, domain, created_at, updated_at. There is no name/slug/type/gstin; business_name is the display name.
- Branches are public.org_locations (id, org_id, name, code, type, status, time_zone, currency, created_at, updated_at). There is no public.locations table.
- users is (id, first_name, last_name, email, status, created_at, updated_at).
- One Latur marketplace tables exist: ol_stores, ol_orders, ol_order_items, ol_products, ol_categories, ol_brands, ol_coupons, ol_media_assets, ol_refunds, ol_partner_devices, ol_booking_enquiries, ol_banners, ol_events, ol_reels.
- There is no online_orders table (supabase/migrations/20260918_create_online_orders.sql was never applied here).

Access model the backend relies on
----------------------------------
The Flutter app never calls Supabase. The backend (backend/) is the only component with database access. It connects with DATABASE_URL, the same connection master-admin uses, and signs users in against master-admin's users table.

That connection bypasses RLS, so the backend enforces tenancy in code:
- every query is scoped to the caller's organization;
- client-supplied references are checked for ownership;
- upserts refuse to update another organization's row.

backend/test/auth-and-tenancy.test.ts attacks this with a second tenant. The database URL and JWT secret live only in backend/.env, never in the app.
